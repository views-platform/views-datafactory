# ADR-038: Public Pipeline Status via Caddy Path Exemption

## Status

Accepted

## Date

2026-06-04

## Context

The data factory generates a static HTML status page (`generate_status.py`, #101) showing which pipeline stages are complete for each data source. This page is valuable for operators, collaborators, and downstream consumers — but it currently sits behind Caddy's `basicauth` alongside the actual data artifacts (grid.zarr, dataframe.parquet).

The status page contains only metadata: source names, stage names, colored dots, and timestamps. No data values, no credentials, no internal paths. There is no security reason to gate it behind authentication.

We want anyone — collaborators, reviewers, downstream teams — to be able to click a link (e.g., from the GitHub README) and see the current pipeline health without needing credentials. This is especially important during incidents: the status page shows which stage failed, and sharing a link is faster than relaying screenshots.

## Decision

Serve specific static HTML pages publicly via Caddy path exemption. All other content under `/srv/views-data/` remains behind `basicauth`.

The Caddyfile uses a `@protected` matcher to apply authentication only to paths that are *not* in the public set:

```
:80 {
    root * /srv/views-data

    @protected not path /status.html
    basicauth @protected {
        views <bcrypt-hash>
    }

    file_server browse
}
```

When additional public pages are added (e.g., health reports, data quality dashboards), they are added to the `not path` matcher list. No new Caddy site blocks, no new ports, no new infrastructure.

### In scope

- Static HTML pages generated by scripts in this repo
- Served from the existing Caddy instance on port 80
- Accessed via raw IP (`204.168.219.108`) until a domain is available

### Out of scope

- Custom web frameworks or dynamic rendering
- GitHub Pages, S3 static hosting, or any external hosting
- Domain name or TLS provisioning (deferred — works fine on raw IP)
- Authentication or access control for the public pages

## Rationale

**WET-before-DRY (C-44).** This is the first public page. We anticipate a few more (health dashboard, data quality report). The right abstraction for serving N public pages will become clear after the second or third page. Until then, the Caddy path exemption is the simplest mechanism that works — one line per page, no new infrastructure, no new deployment steps.

**No sensitive content.** The status page contains source names (UCDP, ACLED, etc.), stage labels (harvest, compilation, etc.), colored status dots, and timestamps. All of this is already public knowledge from the repo itself. The actual data artifacts remain auth-gated.

**Operational value.** During the v1.2.26 deployment, `verify_remote.py` failures required manual investigation to determine which pipeline stage failed. A public status page would have answered this in one click. Sharing a link is faster and more reliable than relaying log output.

## Considered Alternatives

### Alternative A: GitHub Pages

Host the status page on GitHub Pages. The daily cron would commit `status.html` to a `gh-pages` branch or a separate repo.

- **Pros:** Nice URL (`views-platform.github.io/...`), HTTPS by default, no server config changes
- **Cons:** Requires committing generated artifacts to git. Adds git push to the pipeline's critical path. The `views-deploy` service account has a read-only deploy key and cannot push. Would need a separate deploy key with write access, expanding the credential surface.
- **Reason for rejection:** Violates least-privilege (ADR-026). Adds complexity for a cosmetic benefit (nicer URL) that a future domain name would also solve.

### Alternative B: Separate Caddy site block on a different port

Serve public content on port 8080 without auth, keep port 80 auth-gated.

- **Pros:** Clean separation between public and private
- **Cons:** Requires firewall changes (Hetzner + ufw). Consumers need to know which port serves what. Two site blocks to maintain. Non-standard port looks worse in URLs than raw IP.
- **Reason for rejection:** More infrastructure for the same result. The path matcher achieves the same separation with one line.

### Alternative C: Reverse proxy to a static file server

Run a lightweight static server (e.g., Python `http.server`) for public content, reverse-proxied through Caddy.

- **Pros:** Full control over public content serving
- **Cons:** Another process to manage, monitor, and restart. Adds a failure mode. Completely unnecessary for serving static HTML files that Caddy already handles.
- **Reason for rejection:** Over-engineering for the problem at hand.

### Future direction

If the number of public pages grows beyond 3-5, or if we need templating, navigation, or dynamic content, we will reassess. Likely options at that point: a dedicated `/public/` directory with a single path prefix matcher, or a proper static site generator. The current approach is deliberately minimal — it will be obvious when it stops being sufficient.

## Consequences

### Positive

- Pipeline status visible to anyone with the link — no credential sharing needed
- One-line Caddyfile change per new public page
- No new infrastructure, processes, or credentials
- Data artifacts (grid.zarr, dataframe.parquet) remain fully auth-gated

### Negative

- Raw IP in URLs is not user-friendly (mitigated when a domain is provisioned)
- HTTP only, no TLS (acceptable for non-sensitive metadata; see ADR deployment guide Option B)
- Each new public page requires a manual Caddyfile edit (acceptable at current scale)

## Implementation Notes

- Caddyfile change is a manual server operation, documented in `docs/guides/hetzner_deployment_guide.md`
- After editing: `sudo systemctl reload caddy`
- The `file_server browse` directive means directory listing is also public for exempted paths — but `status.html` is a file, not a directory, so this has no effect
- When adding future public pages, extend the matcher: `@protected not path /status.html /health.html`

## Validation & Monitoring

- After Caddyfile change: `curl -s -o /dev/null -w '%{http_code}' http://204.168.219.108/status.html` should return `200` (no auth)
- `curl -s -o /dev/null -w '%{http_code}' http://204.168.219.108/grid.zarr/.zmetadata` should return `401` (auth required)
- If either check fails, the matcher is misconfigured
