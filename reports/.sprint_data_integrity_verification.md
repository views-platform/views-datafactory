# Sprint Plan: Data Integrity Verification

**Date:** 2026-05-26
**Branch:** from `development`
**Goal:** Close the four Tier 2 data integrity concerns by building verification infrastructure that catches silent corruption before consumers train models on bad data.
**Estimated effort:** 12-16 hours of focused work.
**Source:** review-rr prioritize (2026-05-26). Originally from pipeline verification audit (2026-04-30) and consumer parity investigation (2026-04-27).
**Register refs:** C-137, C-138, C-139, C-149. Work package: **Data integrity**.

---

## Context

The data integrity cluster is the highest-severity open work package: all 4 entries are Tier 2. They share a common theme — the pipeline produces output but nothing verifies the output is *correct*. Currently:

- The pipeline writes zarr exports, but no check verifies the export matches the assembled grid (C-137).
- The health check validates timestamps, not data content (C-132 tracks the health check; C-138 tracks post-deploy correctness).
- Consumer parity tests check per-cell deviation rates but not aggregate totals, so systematic undercounting passes the threshold (C-139).
- 603 GAUL admin cells are silently excluded from country-month aggregation because they have no country mapping. This is a known 4% fatality gap (C-149).

These are Tier 2 because: if triggered, consumers train models on silently wrong data. The triggers are approaching — V-Dem production deployment increases the grid from 53 to 75 features, and model training on the served data is the next consumer milestone.

## Task 1: Zarr Round-Trip Integrity Check (C-137, Tier 2)

**Why:** `scripts/export_zarr.py` converts the assembled `.npy` grid to a zarr store for serving. If the export is truncated, produces the wrong dtype, drops features, or silently converts NaN to zero, consumers get wrong data. There is currently no check that the zarr store matches the source `.npy`.

**Register ref:** C-137

### Design

Add a post-export verification step that:
1. Loads the assembled `.npy` grid (source of truth).
2. Loads the zarr store that was just exported.
3. Compares: shape, dtype, feature names, and a sample of cell values.
4. Fails loudly if any mismatch is found.

### Steps

1. Create `scripts/verify_zarr_integrity.py`:
   - Load `data/assembled/grid.npy` and `data/assembled/feature_names.json`.
   - Load the zarr store from `data/export/` (or configured export path).
   - Assert: shapes match exactly.
   - Assert: dtypes match.
   - Assert: feature names match and are in the same order.
   - Assert: `np.allclose(npy_grid, zarr_grid, equal_nan=True)` for a random sample of 1000 cells across all time steps, or for the full grid if memory permits.
   - Print a summary: "Zarr integrity check passed: {shape}, {n_features} features, {dtype}."
   - Exit with code 1 on any mismatch.

2. Add the verification call to `refresh_pipeline.sh` after the export step (step 10 in the 12-step pipeline), before the health check (step 11).

3. Add a test in `tests/test_operational_integration.py`:
   - Verify `refresh_pipeline.sh` calls `verify_zarr_integrity.py` (grep for the script name).

### Acceptance Criteria

- [ ] `verify_zarr_integrity.py` exists and runs standalone.
- [ ] `refresh_pipeline.sh` calls it after export.
- [ ] Script exits non-zero on shape mismatch, dtype mismatch, feature name mismatch, or value mismatch.
- [ ] Script handles NaN correctly (`equal_nan=True`).

## Task 2: Post-Deploy Spot-Check Script (C-138, Tier 2)

**Why:** Even if the zarr export matches the assembled grid, the *served* data could differ — Caddy could serve a stale cache, the zarr store could be from a previous pipeline run, or the deployment step could fail silently. No check currently verifies that what the consumer gets matches what the pipeline produced.

**Register ref:** C-138

### Design

A spot-check script that:
1. Reads a known cell/time/feature from the local assembled grid.
2. Fetches the same cell/time/feature from the remote zarr endpoint.
3. Compares values.
4. Reports pass/fail.

### Steps

1. Create `scripts/verify_remote_data.py`:
   - Accept arguments: `--server-url`, `--n-samples` (default 50).
   - Load local `data/assembled/grid.npy`, `pgids.npy`, `time_steps.npy`, `feature_names.json`.
   - For each sample: pick a random (time, pgid, feature) triple.
   - Fetch the corresponding value from the remote zarr store via `datafactory_query.load_dataset()`.
   - Compare: exact match for integers, `np.isclose` for floats, `np.isnan` agreement for NaN.
   - Report: "{n_pass}/{n_total} spot checks passed."
   - Exit non-zero if any mismatch.

2. Add to `refresh_pipeline.sh` as an optional post-deploy verification step (only runs if `--verify-remote` flag is passed, since it requires network access to the served endpoint).

3. Document in `docs/guides/server_operations.md` as part of the post-deployment checklist.

### Acceptance Criteria

- [ ] `verify_remote_data.py` exists and runs standalone.
- [ ] Fetches from the remote zarr endpoint and compares against local grid.
- [ ] Reports pass/fail with sample count.
- [ ] Handles NaN values correctly.

## Task 3: Aggregate Total Verification (C-139, Tier 2)

**Why:** Consumer parity tests (`tests/test_consumer_parity.py`) check per-cell deviation rates: what fraction of cells deviate from a reference by more than a threshold. This catches random cell-level errors but misses systematic errors. If the pipeline undercounts fatalities by 10% uniformly across all cells, per-cell rates pass (each cell is "close enough") but the aggregate is wrong.

**Register ref:** C-139

### Steps

1. In `tests/test_consumer_parity.py`, add aggregate verification tests:
   - For each UCDP feature: compare `np.nansum(grid[:, :, :, feature_idx])` against a known reference total (from the consolidated store or a verified snapshot).
   - Tolerance: 0.1% for integer-valued features (fatalities, events), 1% for derived features.
   - Add a test that the total number of non-zero cells per feature matches the reference within 1%.

2. Create reference totals:
   - Run the current pipeline (known-good state).
   - Extract per-feature aggregate totals and save to `tests/fixtures/aggregate_reference.json`.
   - Include: sum, count_nonzero, count_nan per feature per time step (or per-year aggregate).

3. Add a guard: if the reference file is missing, skip the test with a clear message (the reference needs to be generated on a machine with the full pipeline output).

### Acceptance Criteria

- [ ] Per-feature aggregate sum comparison exists.
- [ ] Per-feature non-zero cell count comparison exists.
- [ ] Reference file `tests/fixtures/aggregate_reference.json` exists (or test skips with clear message).
- [ ] Tolerance thresholds documented in test docstrings.

## Task 4: GAUL Unmapped Cells Documentation and Warning (C-149, Tier 2)

**Why:** 603 PRIO-GRID cells have no country mapping in the GAUL admin boundary data. When `grid_to_country_month` aggregates grid data to country-month format, these cells are silently excluded. This represents approximately 4% of total fatalities. Consumers training country-month models don't know about this gap.

**Register ref:** C-149. See also `reports/postmortem_cm_unmapped_gaul_cells.md`.

### Steps

1. Add a consumer-facing warning to `docs/guides/consumer_data_guide.md`:
   - In the "Country-Month Aggregation" section (or equivalent): note that 603 cells are excluded due to missing GAUL country mapping.
   - Quantify the impact: ~4% of fatalities in affected regions.
   - List the regions most affected (from `reports/postmortem_cm_unmapped_gaul_cells.md`).

2. Add a runtime warning in `datafactory_adapters/grid_to_country_month.py`:
   - When the function runs, if any cells are excluded due to missing country mapping, emit a `warnings.warn()` with the count of excluded cells.
   - Make the warning actionable: "N PRIO-GRID cells excluded from country-month aggregation due to missing GAUL mapping. See docs/guides/consumer_data_guide.md."

3. Add a metadata field to the zarr store's `.zattrs`:
   - `"gaul_unmapped_cell_count": 603`
   - `"gaul_unmapped_cell_note": "These cells are excluded from country-month aggregation"`
   - This allows programmatic consumers to check for the gap.

4. Add a test: `grid_to_country_month` with a grid that has events in unmapped cells emits the warning and excludes those cells from the output.

### Acceptance Criteria

- [ ] Consumer data guide documents the 603-cell gap.
- [ ] `grid_to_country_month` emits a warning when cells are excluded.
- [ ] Zarr `.zattrs` includes `gaul_unmapped_cell_count`.
- [ ] Test verifies warning emission and correct exclusion.
