## The thing to read if you read nothing else

**A mutation written to test a guard was committed and pushed into the release branch, and the only
thing that stopped it shipping was a guard the same epic had written two days earlier.**

Commit `8742f06` carried the line `declared = None  # M-01 MUTATION: revert the declared-cell fix`.
With it, `_place_events` never consulted `priogrid_gid` and placed every row from its coordinates —
**the exact defect this release exists to fix**, restored by the audit meant to prove it was fixed.
Auto-merge was already armed on the gate.

The delivery guards from #551 went red: five failures, *"allocator chose 6 cells, grid delivered
1"*. And the log line added for ADR-003's fail-loud requirement printed
`0 rows used the declared cell, 0 had none, 0 were unusable` while mass was still being placed — an
impossible combination that named the cause faster than any assertion did. **The observability was
not decoration.**

Three things had to go wrong together, and all three did, in order:

1. the mutation audit ran against a tree holding uncommitted work;
2. that tree was then verified by **grepping for strings I had added** — `n_declared_invalid`,
   `pgid_field`, `reject_ignored_declared_cell`, all present — rather than by reading the diff. The
   mutation changed a line I had not thought to grep for. **A spot check for what you wrote cannot
   see what someone else rewrote.**
3. auto-merge was armed on a gate whose exit code had not been read, which is why this needed a
   disarm rather than a revert.

Restored in `bf39bf5`, before the release was cut.

## What the defect was

ADR-015 chose `priogrid_gid` as the placement authority in July 2026. Nothing read it.

`proportional` allocated a summary event's fatalities across the cells of the admin-1 region or
country UCDP declares, weighted by observed activity, and wrote the chosen cell into
`priogrid_gid`. The event compiler then called `latlon_to_pgid` on the row's unchanged
`latitude`/`longitude` and placed the row where the source centroid had always put it.

Every allocated row therefore arrived back in the cell it came from. **1,128,236 fatalities —
26.49% of delivered mass — sat in a cell other than the one chosen for them.** Event 463131 was
allocated across 18 cells and delivered into 1.

Every conservation invariant held throughout, because each one compared a stage's output to that
stage's own input. The allocation was correct, recorded in the right field, and read from the wrong
one. **Conservation at four boundaries says nothing about a boundary between two of them.**

The previous release, v1.18.0, shipped the temporal half of this fix and not the spatial half, and
its own pre-registered numbers recorded three failures out of four. That table is in
[its post-mortem](2026-11-11_release_v1180.md).

## What shipped

`CompilationConfig.pgid_field` (default `None`) names a column carrying a precomputed cell.
`_place_events` prefers it when the config names it and the value is in range, and falls back to
`latlon_to_pgid` otherwise, counting both. `_required_columns` requests the column only when it is
named.

ACLED is unaffected by construction, two independently sufficient ways: both ACLED compile call
sites pass `pgid_field=None` explicitly, and the ACLED viewpoint parquet has **no `priogrid_gid`
column at all**. ACLED does not allocate, so for ACLED `latlon_to_pgid` *is* the correct authority.

Worth knowing before the next change: `compile_grid.py`'s `--pgid-field` **defaults to
`priogrid_gid`**, so a future ACLED path routed through that script rather than through the ACLED
one would silently acquire the new authority — a regression, not a fix.

### The qualitative result, which matters more than any bound

The largest state-based cell in month 504 is now **150197** — the cell the allocator *chose*.
Before the fix it was **148759**, the source centroid. The mass moved from the cell the coordinates
named to the cell the declaration named. **That is the defect, inverted, visible in the served
artifact.**

### What "implied" means, stated rather than glossed

Rows 1, 2, 9 and 10 are **not** directly measured. The served grid holds cell-month aggregates and
carries no event ids, so no per-event question can be asked of it.

The instrument is an exact reconciliation: every `(declared cell, month)` total the viewpoint
predicts, compared against the grid compiled from it. **441,195 cell-months predicted, 441,195
checked, 0 mismatched.** If every cell-month total matches, no mass moved between cells, so each
event's footprint arrived as allocated.

That is an aggregate identity, not a per-event count. For it to hold while an event was still
displaced, the displacement would have to cancel exactly across all 441,195 cell-months, for 26.49%
of fatality mass spread over 60,105 events. Treated as conclusive, and recorded as an **entailment,
not a reading**.

### The one limit on that evidence

The reconciliation ran against a **local** viewpoint and a grid compiled from that same viewpoint.
It proves the code delivers the declaration exactly. It does **not** prove production's grid matches
production's viewpoint, which would need the production viewpoint parquet.

What covers production is the other two readings, both from production artifacts: the server's own
counter — `Placement authority 'priogrid_gid': 2796238 rows used the declared cell, 0 had none, 0
were unusable`, with no accompanying warning — and the five served-store figures above.

### A number that looks alarming and is not

The same diagnostic prints `DISPLACED: 1,128,236 (26.49%)` and
`event 463131: allocated cells 18, DELIVERED cells 1` **after** the fix, unchanged. Those are the
#548 diagnosis: the gap between an allocated row's declared cell and the cell its *coordinates*
imply. The allocator never rewrites `latitude`/`longitude`, so that gap is permanent by design. The
fix makes the compiler stop reading the coordinates; it does not make the allocator start rewriting
them. **Reading those lines as a live failure is reading the instrument, not the data.**

## The independent mutation audit

48 mutations across two clean-context subagent runs. The full record, including the three
acceptance items that can no longer be met in form, is
[`reports/2026-11-12_mutation_audit_epic547_guards.md`](../2026-11-12_mutation_audit_epic547_guards.md).

The two findings that belong in this release's record:

**The guards for the declared-cell seam hold.** Seven independent mutations were caught every time,
by the right guard, with messages pointing the right way — including the shipped defect itself,
restored deliberately this time.

**A guard written against one magnitude error pins that error's scale rather than the property.**
The guard written to catch a weight-magnitude defect used a fixture of 60/30/10 — shares exactly
representable at two decimal places — so `round(deaths / total, 2)` passed the entire suite, 2,547
tests. Changing four fixture numbers to primes moved the detection boundary from between 1 and 2
decimal places to between 6 and 7. **One fixture line, five decimal places of sensitivity.**

## What to do differently

1. **Never run a mutation audit against a tree holding uncommitted work.** The audit's revert and
   your own unfinished edits are indistinguishable afterwards.
2. **Verify a tree by reading the diff, not by grepping for strings you expect to find.** A spot
   check for what you wrote cannot see what someone else rewrote. This is the specific step that
   let a mutant through.
3. **Never arm auto-merge on a gate whose exit code has not been read.** Arming it first is what
   turned a revert into a disarm.
4. **A brief that forbids reading the author's prose must not name a command that prints it.** The
   re-audit's independence was partially compromised because the brief said
   `git show --stat <sha>`, which prints the full commit body. Use `git show <sha> --format=""`.
5. **Write a subagent's report to a file in its worktree before the subagent returns.** The
   per-mutation evidence from 48 mutations exists nowhere now.
6. **Do not generalise a scoped audit's finding past its scope without re-running it there.**
   *"None of the epic's guards caught it"* was reported to the operator as *"unguarded in CI"*,
   which was false — a June 2026 test catches it. The real absence was one seam lower, and was
   found by **moving the mutation rather than reasoning about it**.
7. **Capture the run's own duration and peak memory while that run is the current one.** The
   previous release's post-mortem has two permanent holes for want of this.

### Did the previous post-mortem's lessons recur?

v1.18.0's list is nine items, four of them added retrospectively by this epic. Of the five that
existed at the time:

- **Item 4 recurred in substance** — *"switching a profile means auditing every consumer of the old
  artifact path"*. The same shape appears here as a **field** rather than a path: `priogrid_gid` was
  written by one stage and never read by the next, and no inventory of its consumers existed to
  audit. Generalised and recorded as the headline above.
- Items 1, 2 and 3 did not recur. Item 5 onwards did not exist yet.
