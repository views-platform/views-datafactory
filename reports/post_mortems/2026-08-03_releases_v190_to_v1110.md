# Post-Deployment Post-Mortem: v1.9.0 → v1.11.0

**Date:** 2026-08-03
**Author:** Simon Polichinel von der Maase, Claude Code
**Scope:** Go-public + first PyPI release (v1.9.0); pandas as an output format and the consumer seam (v1.10.0); release-procedure repair, base-docs audit, monitoring, dependency-floor correction (v1.11.0)
**Branch:** development → main, three releases
**Releases:** v1.9.0 (2026-07-27) · v1.10.0 (2026-08-01) · v1.11.0 (2026-08-03)
**Commits:** 28 in `v1.9.0..main` · **PRs:** 30 merged since 2026-07-27
**Concerns:** C-318 through C-339 registered in this window; 6 of them already resolved
**Previous post-mortem:** [v1.5.0 → v1.6.0 (pre-deploy)](2026-06-29_predeployment_v160.md)

---

## The thing to read if you read nothing else

**Nine releases shipped between the last post-mortem and this one, and none was written.**

The v1.6.0 post-mortem's *first* "do differently" item was: *"Write post-deployment postmortems
immediately after deployment."* It also observed that the same item had been missed for v1.4.0 and
v1.5.0. So the convention has now failed to be applied to eleven consecutive releases, and it
recorded itself failing before failing nine more times.

That is not an aside. It is the same shape as almost everything else this document reports: **a
written record that was true when written and stopped being true without anything failing.**

## What we did

Three releases in eight days, plus a long governance-repair effort between the last two.

The sequence was not planned as a unit. v1.9.0 was a deliberate milestone — repo public, first PyPI
publish. v1.10.0 came out of a single question ("is this repo pandas-free?") that turned into an
epic. v1.11.0 exists only because an audit found a dependency floor had frozen a transitive package
for six weeks, and there was no way to ship the correction except as a release.

---

## What shipped

### v1.9.0 — public, and on PyPI (2026-07-27)

Repository made public. First PyPI publish via Trusted Publishing (OIDC, no stored token), rehearsed
on TestPyPI first. First-time-user guide, guides index, credential-guide gaps closed. Server SSH made
key-only after a pre-public audit found `PasswordAuthentication` effectively enabled — the stock
config only *comments* the directive, so an internet-facing SSH port had been accepting password
attempts throughout (C-88 addendum).

Test-suite integrity restored in the same window: C-319 (lock contamination causing 42 errors per
run since v1.8.1), C-320 (deploy gates permanently red in CI), C-321 (a 401 surfacing as a raw
aiohttp error, found by the TestPyPI rehearsal).

### v1.10.0 — pandas becomes an output format (2026-08-01)

`pandas` moved to a `[pandas]` extra, with the caveat recorded in `pyproject.toml` that the extra
**gates nothing today**: xarray requires pandas, so no installable configuration lacks it. The change
makes pandas *not imported*, not *not installed*. Import purity is enforced by **subprocess** probes,
because an in-process assertion is meaningless once pytest has loaded the module.

`matplotlib` was demoted and then **restored** (C-334): views-hydranet imports it at module level
without declaring it, and four views-models environments receive it through us. Removing it would
have broken clean builds while leaving upgraded local environments green, since pip never prunes
orphaned transitive dependencies.

`load_dataset` gained a `storage_options` seam so a new data source can bring its own credentials
instead of waiting on a netrc entry on our server. Adapters split so legacy and frame-native outputs
stopped sharing a file.

### v1.11.0 — governance repair (2026-08-03)

**`src/` is untouched.** The wheel is byte-identical to v1.10.0 apart from metadata. The single
consumer-visible change is `views-frames>=1.0` → `>=1.10.2`, and that floor is the entire reason the
release exists. Everything else — the release-procedure consolidation, the docs gate, the base-docs
audit, the monitoring work — is documentation, CI, and tests.

## The spine: one failure mode, six instances

Each of these was **true when written**. Each stopped being true without anything failing.

| # | Instance | Where |
|---|---|---|
| 1 | `"9 sources"` — a count matching no artifact in the repo, repeated in 8 places | C-164 |
| 2 | logrotate configured for a path the pipeline had left; `missingok` reported success nightly for four months | C-330 |
| 3 | ADR-026: *"Public GitHub is safe"* — while a working Caddy password sat in committed post-mortem prose | #391 |
| 4 | ADRs citing `lab_grid/`, a package views-metric-lab **deleted** in their commit `6e1a34d` | C-336 |
| 5 | `docs/validate_docs.sh` — correct, passing, and wired to nothing: not CI, not pytest | — |
| 6 | `views-frames>=1.0` let `uv.lock` freeze at 1.0.0 for six weeks | C-337 |

None of these produced an error. Several produced *green*. #2 reported success every night for four
months; #5 was a file that looked like assurance.

**Two were caught by the operator, not by the audits.** #2 and #6 both. On #6 the operator knew that
views-frames had changed how MAP and HDI are computed and said so; the audit had cleared the floor
minutes earlier with evidence — a clean-venv install proving every imported symbol works at 1.0.0.
The evidence was real and the question was wrong. A floor constrains the **resolver**, not the import
list, and the lockfile — where the actual damage was — was never opened.

**#6 happened inside the audit written about this exact failure mode, one day after writing it.**
That recurrence is why C-337 is Tier 2 and open rather than a tidy fix, and why C-336 is a standing
entry rather than four one-off corrections.

## What we found: the good

### 1. Branch protection earns its keep immediately

Enabled 2026-07-31 on both long-lived branches with `enforce_admins: true` and no bypass. It caught
real errors of mine within hours — a PR that would have merged with `test` still pending, and later
a change that broke three tests in a fresh clone but passed locally because the file was still on
disk. Only CI can catch that class; a local suite structurally cannot.

### 2. Verification by artifact, not by checkmark

Both PyPI publishes were confirmed by **installing from PyPI into a clean venv** and importing all
nine packages, not by a green workflow. This caught nothing — but it is the only reason we can say
the packages work rather than that the pipeline reported success. For v1.11.0 the check also proved
the point of the release: a fresh install resolves views-frames **1.10.2**, not the frozen 1.0.0.

### 3. Drilling guards found three real defects before they shipped

- The **freshness check** false-positived against the *live, healthy* status page. It searched the
  page text for `stale` and `missing`; the page carries a legend — `● OK ● Stale ● Missing` — so
  those words appear on every healthy page. Shipped, it would have opened an issue daily until
  muted. **ADR-051 specified the paid vendor check the same way**, so buying the feature would not
  have helped.
- `test_register_changelog.py` caught **its own author** reintroducing a `Prior:` chain into the
  register header, one day after being written to prevent exactly that.
- The retargeted architecture-doc guards were drilled by removing SHDI from the README and watching
  them fail on the right assertion.

A guard that has only ever passed is not known to guard anything. Three for three, in one week.

### 4. Cross-repo checking prevented a wrong "fix"

The base-docs audit had `audit_data_parity.py` on its stale list until the sibling repo was opened —
it exists, in `views-models/models/bright_starship/`. Deleting it would have been C-330's error
committed *inside* the audit written to catch that error. The resulting guard therefore deliberately
does **not** assert that every referenced path exists: a guard that cannot distinguish "deleted" from
"lives elsewhere" teaches people to remove true references.

## What we found: the gaps

### 1. Nine releases with no post-mortem

Covered above. The convention's own enforcement mechanism — statusing the previous document's items
— cannot run if the documents are not written.

### 2. Deploy gates only run locally

The topology gates are skipped in CI because the default checkout is shallow and `git merge-base`
cannot answer (C-320). Detection therefore depended on somebody running the full suite at the right
moment. After v1.10.0 that happened four hours late, by accident, and had been silently true after
**every** prior release. `release-topology.yml` now checks daily with full history, but the gates
themselves still skip in the PR job.

### 3. C-337's untested tail

The views-frames floor is fixed. **Nothing has checked the others.** `numpy>=1.26,<3`,
`pyarrow>=14,<20`, `zarr>=2.16,<3` have the same structure, and the same "the lock froze at the
floor" failure is available to every one of them. C-337 is deliberately left open for this.

### 4. Freshness detection is weaker than availability

C-338. Better Stack's free tier cannot do content checks, so freshness lives in a GitHub-scheduled
workflow: daily rather than 3-minute, an issue rather than an e-mail, and GitHub may delay `cron`
under load. Late notice of stale data, not wrong data — but the asymmetry should be known.

### 5. Observations in a sibling repo

views-faoapi has **one** monitor where its own runbook describes two; the second (`/health`, content)
is what catches a stale forecast behind a green light — the failure their C-50/C-170 records. It also
logged three `/ping` timeouts in a single day (2026-07-30), 7–8 minutes each. Not this repo's to fix;
recorded because nobody else is looking.

## Incident: `refresh.log` destroyed during the C-330 fix

**Severity:** data loss, non-recoverable. **Registered:** C-339, Tier 3. **Cause:** mine.

### What happened

Fixing C-330 required rewriting `/etc/logrotate.d/views-datafactory`, which needs root. I gave the
operator a `sudo tee ... <<'EOF'` heredoc to paste. Their terminal joined the first two lines, so the
shell received:

```
sudo tee /etc/logrotate.d/views-datafactory > /dev/null <<'EOF' /home/views-deploy/views-datafactory/logs/refresh.log {
```

`tee` writes to **every** file it is given. Running as root it wrote the config text into the
logrotate file, into `refresh.log`, and into a file named `{`.

**528 KB → 150 bytes.** Four months of pipeline run output.

### Why it was unrecoverable

No backup, and no rotated copy — **because the rotation being fixed had never run.** The fix for the
missing rotation destroyed the thing the rotation would have preserved.

### Impact, honestly

Lost: run output — start/finish lines, per-source counts, recorded errors. Not lost: the provenance
ledgers under `data/`, the status page, healthchecks.io ping history, git history. Nothing reads
`refresh.log`; the pipeline appends to it. The loss is diagnostic history, not function or data. It
also destroyed the last copy of the leaked GDL token, revoked two days earlier and worthless.

### Three failures, in order

1. **Format.** Single-line commands had been used with this operator all session, *precisely because
   pasting was already causing trouble*. Switching to a heredoc for the one root-privileged write was
   the error.
2. **No dry run.** The command wrote on first execution. It could have printed to stdout for
   inspection and been re-run through `| sudo tee` once confirmed.
3. **A backup that protected the wrong thing.** The command backed up the *config it was replacing*
   and not the *log it could reach*. The backup protected what I was thinking about.

### Why Tier 3 rather than Tier 4

The consequence was mild; the mechanism was not. A root-privileged command whose failure mode is
*writing to an unintended path*, handed to a human to paste blind, lands differently against a data
directory or a zarr store. The register should carry the mechanism, not the luck.

### What changed

**Standing rule:** commands given to a human to paste are one line. Multi-line content goes in an
editor and the edit is described — which is what worked immediately afterwards.

## What we'd do differently

Only items that will actually be done, or that are being closed. Carrying an item a sixth time is not
a plan.

### Closed as not worth it

- **Per-step duration logging** and **skip-decision logging.** Carried from at least v1.2.x through
  v1.6.0, and five releases further. Nobody has needed them in any incident since. Closing them
  honestly beats a tenth carry-forward.

### Adopt

1. **Check every dependency floor against its lock, not just against imports.** C-337's tail. The
   question is not "does our code work at the floor" but "what does the floor permit, and what has
   the lock chosen". One command, never run before this week.
2. **Run the deploy topology gates in CI with `fetch-depth: 0`** — on a schedule, not in the PR job.
   `release-topology.yml` already does this for one gate; the rest should follow. Never in the PR
   job: between a release and its back-merge the branches *are* diverged, and reddening every PR for
   that is C-320 again.
3. **Post-mortems: change the cadence or change the claim.** Eleven consecutive misses means
   per-release post-mortems are not happening. Either write a five-line deployment note at tag time
   — date, version, duration, obstacles, anomalies — as an automated stub, or amend the convention to
   say post-mortems are per *effort* rather than per *release*, and stop recording a failure against
   a rule nobody follows.

### Keep doing

- **Drill every guard by breaking it.** Three real defects this week, including one in a guard's own
  author.
- **Verify claims about the world by observing the world.** C-330 was settled only by `stat` and a
  dry run on the server. Reading the repo would never have answered it — and reading an archived plan
  produced the wrong answer with confidence.
- **Record corrections rather than quietly rewriting.** C-330's entry now reads correct → corrected
  into wrong → confirmed correct. That history is more useful than a clean entry would have been.
