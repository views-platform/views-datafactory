## The thing to read if you read nothing else

**Every gate was green and the code was still wrong.**

The epic's code passed the full suite on two Python versions, `ruff`, `mypy --strict`, a secret
scan, the documentation validator, all fourteen register-reading test files, and **five mutation
drills administered by the author**. On that evidence the operator asked an unprompted question —
*"do we need a code review first? Would that be prudent?"* — and an independent review then found
**four defects, all in code written for this epic**. Two of them were in the failure path this
release exists to fix: the ledger entry meant to record *why* a harvest failed could itself raise
and replace the reason, and the operator-facing line told the operator to go read an entry that
several failure paths never write.

The epic's own subject reappeared inside its own remedy, and nothing we run noticed.

Then it got worse, in the most useful way available. The five mutation drills that had reported
"caught" were **measuring stale bytecode**. The drill restored each production file by `cp` within
the same *second* that pytest had compiled the mutant; Python's source-staleness check compares
whole seconds, so the mutant's `.pyc` stayed in use after the file was restored. The drills were
redone with `__pycache__` cleared around every step and all four guards were genuinely caught — so
no conclusion drawn from them is wrong — but **they had been reporting the right answer for the
wrong reason**, and the same mechanism would equally report "survived" while measuring restored
code. Every mutation drill run in this repository before 2026-10-30 has that exposure.

The v1.15.0 post-mortem named its spine as *"a written record that was true when written and
stopped being true without anything failing"* and observed that **every instance in that window
was found by a human asking an unprompted question**. Both halves recurred here, unchanged:

- **C-72** (`reports/technical_risk_register.md:1400-1403`) described this exact defect, at these
  exact two locations, and carried the trigger *"if UCDP or ACLED starts returning 429s during
  multi-page harvest **(not observed to date)**"*. The trigger had fired. The register went on
  stating the parenthesis.
- **ADR-043:99** states a disclosure obligation on every data delivery containing supplemented
  cells. Nothing propagated it. A downstream consumer carried a wrong explanation of those cells
  for months, and it surfaced only because an unrelated coverage check went looking for something
  else.
- The review that found four defects happened because a human asked whether it would be prudent.
  Not because anything scheduled it.

**The new finding this window adds** is narrower and more actionable than "try harder": *the author
cannot audit their own guards.* The `falsify` skill's own measurement — guards that cannot fire
recorded in **9 of 18 repositories** across this platform, measured 2026-08-23 — is the base rate,
and this window is a clean instance of it. (The measurement itself is not held in this repository,
so it is cited by date rather than by path: 15 of the 32 platform repositories are private, and the
public record does not carry their file paths, per C-358.) The author's five drills were
self-administered, and the thing they failed to imagine was the filesystem timestamp granularity
underneath them.

**One thing did hold.** The v1.15.0 post-mortem ended with *"if it fails again, the honest move is
to delete the convention rather than record a fourth self-indictment."* This document was written
the same night as the release it describes. First time in five releases.

## What we did

One release, from one incident, deliberately widened to the two defects the incident exposed rather
than the one that caused it.

**The trigger.** On **2026-10-21 00:07 UTC** the monthly production cron (`0 0 21 * *`, its first
ever run on `v1.15.0`) aborted at step **1/14** when ACLED returned `429 Too Many Requests` partway
through a 71-request cursor walk. Nothing was written, no export ran, and healthchecks.io fired as
designed.

**Two defects, one incident.** The run aborted because we refuse to wait out the one 4xx status
whose entire meaning is *wait and retry*. It was expensive to diagnose because the failure path
records a step number and an exit code and never a reason. The epic treats these as separate
stories because they have separate remedies, and a release that fixed only the first would have
left the next unrelated failure exactly as expensive to diagnose.

A third thread rode along: the same aborted-then-rerun pipeline produced the measurement #501 had
been waiting for since 16 October, and that figure needed recording while it was in hand.

## What shipped

### S1 (#511) — 429 is the one 4xx that means *later*

`retry.py` classified all of `[400, 500)` as permanent and raised before the retry loop was
reached, so `max_retries` was structurally dead for 429 — the one 4xx that means *retry later*
(RFC 6585 §4), commonly with `Retry-After`. 429 is now carved out ahead of the fail-fast branch via
`_RETRYABLE_CLIENT_STATUSES = frozenset({429})`; 400, 401, 403, 404 and 408 still fail immediately.

**Marking it retryable alone would have fixed nothing.** The generic backoff was
`delay = 2**attempt + random.uniform(0, 1)`, and every call site passes `max_retries=3`, so the
total wait before giving up was **~3 seconds**. A fix that merely reclassified the status would have
looked like a fix and failed the next 429 identically. So 429 got its own policy:
`_RATE_LIMIT_BASE_DELAY_S = 30.0` (borrowed from `ucdp_annual.py:58`, and explicitly unmeasured for
ACLED), `_RATE_LIMIT_JITTER_S = 5.0`, `_RATE_LIMIT_MAX_WAIT_S = 120.0`.

`Retry-After` is honoured for delta-seconds only, parsed with `int()` so `nan`, `inf`, `1e9999` and
`45.5` are rejected by construction. The HTTP-date form is deliberately **not** parsed: a skewed
provider clock yields an absurd sleep, and an unparsed date costs nothing because it falls back to a
real 30s wait. A value **above** the ceiling fails fast with the number in the message, because
Cloudflare-fronted 429s routinely carry 3600 or 86400 and honouring one would stall an unattended
cron for a day.

**Worst case, stated as a number:** two sleeps per request, **≤100s including jitter** — 35s then
65s. Boundary-true at exactly 100s.

**The measurement this fix could not make.** The old fail-fast log line emitted only the status code
and a redacted URL, so the 21 October incident did **not** record whether ACLED sent `Retry-After`.
"Measure before fixing" could not be satisfied. The new WARNING line therefore logs the header
value or the literal `absent`, which is what makes the borrowed `30.0` self-correcting by
21 November rather than folklore. Stated as a known weakness, not hidden.

**Governance.** `docs/ADRs/027_harvest_count_verification.md:39` had decided the opposite in
writing — *"The HTTP retry layer should continue to fail fast on 4xx"* — on the reasoning that only
pagination context makes retrying an ambiguous status safe. That rationale is specific to
*ambiguous* codes: UCDP's 400 could mean anything. **429 is never ambiguous.** ADR-027 is therefore
amended in place to narrow *"fail fast on 4xx"* to *"fail fast on 4xx except the statuses that mean
'later' — currently 429 alone"*, superseding rather than rewriting so the April reasoning stays
readable. UCDP's 400-as-rate-limit stays at the pagination layer, untouched. One sentence appended
to ADR-018's Timeout Policy. No new ADR.

### S2 (#513) — a failed harvest writes its reason where an operator can read it

ADR-011 consequence #2 already required a provenance ledger entry with `outcome: "failed"`.
`vdem.py:174-183`, `shdi.py:234-245` and `ghspop.py:181-189` complied. ACLED did not — its only
`"outcome": "failed"` write was reached *after a successful fetch*, when validation failed. So this
is **conformance to an existing ADR**, not a new mechanism.

The error string is redacted at the write, not assumed clean from the source. This is the C-322
class exactly: a token reached `logs/refresh.log` through a `requests` exception message, and the
repo is public. Errors from `request_with_retry` are already redacted; errors from anywhere else are
not, and the ledger is world-readable on the server — which is the entire point of the change.

### S3 (#514) — the export ledger accounts for its own elapsed time

The 21 October entry's four phases summed to 17,017.2s of a 17,773.8s export. The missing **756.6s**
was printed to `logs/refresh.log` as `other` and never persisted. Logs rotate monthly and keep 12;
the ledger does not rotate, which was the stated reason for writing to it at all. **The surviving
copy was the incomplete one.** `other` is now persisted, and the version-bump rule — undetermined by
the one written sentence in `ARCHITECTURE.md:39` — is now written down with the adding-versus-
changing-a-key distinction made explicit.

| phase | seconds | share |
|---|---:|---:|
| `scan` | 8,434.2 | 47.5% |
| `write` | 8,558.9 | 48.2% |
| `other` | 756.6 | 4.3% |

Pipeline total 26,708s (7h25m), so the export was **66.5%** of this run — not 88%, because
2026-10-16 skipped assembly under ADR-041 and this run did not. No operator-facing document should

The pre-registered criterion was *"if `scan` comes in under ~25% of the export, the strided-memmap
explanation is refuted and I stop advancing it."* `scan` is **47.5%** — the explanation **survives**.
The synthetic baseline was 10.1% and the smallest phase, so the predicted inversion occurred.
Surviving a refutation test is not confirmation, and #501's own objection stands: 43 → 79 features
does not turn 14 minutes into 307 under any linear reading.

### S5 (#516) — the spike, and the premise it had to fix first

The spike was going to test whether crossing the RAM boundary inverts `scan`'s share. **It could not
be run as designed, because its premise was wrong.** The documentation asserts 4 vCPU / 8 GB in
**13 occurrences across 11 files**, and ADR-030 and ADR-035 both rest on "8 GB". The box measured
**8 vCPU AMD EPYC-Genoa, 15 GiB RAM, 15 GiB swap, up 147 days**. The 8 GB premise is precisely what
made the RAM-boundary hypothesis look well-founded, and it would have produced a confidently wrong
answer had the spike not been re-premised first.

Re-premised, it measured something better: **`scan` re-reads the whole 37.355 GB grid once per
feature.** 79 passes, 2.951 TB from disk. F is the contiguous axis, so `grid[:, :, :, i]` strides by
316 bytes and yields **1.27% page utilisation**; `utime/wall = 0.0198`; read amplification **8.001×**
at F=8, measured via `/proc/self/io` `read_bytes`. The cost is **O(F²)** in feature count, so it
worsens with every feature added. `scripts/export_zarr.py:252-263`; evidence in
`reports/investigation_zarr_export_cost/e1_results.md` and `e1_raw_2026-10-22.jsonl`.

**Nothing was optimised**, per the spike's own terms and the v1.15.0 post-mortem's instruction not
to optimise the export before a cause exists. A cause now exists for `scan`. It does not for
`write`.

The June-versus-October comparison that motivated the spike is **confounded and should not be
re-used**: the June laptop had 32 GB + 2 GB swap against the server's 32 GB — within 6% — *and* ran
43 features against today's 79. Two variables moved at once. Anyone re-opening the RAM-purchase
question from that delta will re-derive the same wrong conclusion.

## Incident: the four defects an independent review found after every gate was green

**What happened.** With the epic complete, all gates green and PR #521 (`development` → `main`)
open, the operator asked whether a code review would be prudent. It found four defects, all in code
written for this epic, all of which had survived the full suite on two Python versions, `ruff`,
`mypy --strict`, a secret scan and five author-administered mutation drills.

**The two that broke the epic's own subject.**

1. **The recorder could replace the reason.** `_append_failed_fetch_entry` called
   `append_ledger_entry` unguarded, from inside `except Exception as exc:` immediately before a bare
   `raise`, at two call sites. `append_ledger_entry` re-raises `OSError`. On a full disk the ledger
   write would raise *from inside the handler*, destroying the `__context__` chain and surfacing
   "No space left on device" where the fetch error belonged. **The story written to stop a failure
   lying about its cause shipped a new way for it to lie.** Now wrapped, with a `logger.exception`
   that says explicitly which of the two errors matters, and a "Never raises." paragraph in the
   docstring explaining why.

2. **The operator line promised an entry that may not exist.** `scripts/harvest_acled.py` printed
   *"recorded in {ledger_path} (outcome: failed)"*. Several paths reach that line with no entry
   written — most commonly `get_acled_credentials` raising before the loop on a missing
   `ACLED_USERNAME`/`ACLED_PASSWORD`, the most frequent operator error of all. Because the ledger is
   append-only, an operator sent to grep it would find a **previous** run's failure and read it as
   this one's. A confident wrong reason is worse than no reason — which is the defect this story
   exists to fix. The line now says *"look in … for an entry with outcome: failed … check its
   timestamp, the ledger is append-only"*, and the reason printed immediately above it is the
   authority for this run.

**The two in `retry.py`.** Jitter was applied *outside* the ceiling, so the clamp bounded 120s and
the actual sleep could reach 125s; and the rate-limit delay was computed eagerly even on the final
attempt, where it is discarded. Both fixed. The first implementation of the second fix used a
closure and `ruff` rejected it with **F821** (`exc` is deleted at the end of the `except` block that
binds it) and **B023** (late binding of `attempt`) — a latent bug, not a style complaint — so it was
backed out for an explicit `rate_limited: bool` flag computed inside the function.

**Honesty correction on S1.** A later falsification audit established that the 125s overshoot was
**unreachable in production**: every `max_retries` in this repository is 3 (one literal, nine
defaults), so the sleeps are 35s and 65s and the clamp never binds. It is a consistency fix, not a
behavioural one, and the commit that landed it describes it without that qualification. The ≤100s
worst case above is unaffected.

**Why it belongs in a post-mortem rather than a correction.** Four defects in roughly 1,200 lines of
new code is not remarkable. **The gates being green is.** The suite, the type checker, the linter
and five mutation drills are the entire mechanism this repository relies on to know that a change is
right, and they were unanimous and wrong. The only thing that caught it was a human wondering aloud
whether more scrutiny was warranted — which is the same detection mechanism the v1.15.0 post-mortem
identified, and it is still not a mechanism.

## Incident: five mutation drills that measured the wrong bytes

**What happened.** After the four fixes landed, the full suite failed on one of the author's own new
tests while that test passed in isolation. The tempting conclusion was an isolation quirk.

**What it actually was.** Measured rather than assumed: `_rate_limit_delay` was recorded as called
with `[0, 1, 2]`; `inspect.getsource` showed the correct code; and a direct call both raised as
expected **and** recorded a delay computation that the code on disk cannot produce. `retry.py` had
mtime `00:37:02` while `retry.cpython-313.pyc` was written at `00:37`. **Python's source-staleness
check compares whole seconds.** The drill's `cp` restore had landed inside the same second pytest
compiled the mutant, so the stale `.pyc` stayed authoritative.

**What it invalidates.** Not the conclusions — the drills were redone with `__pycache__` cleared
around every step and all four guards were genuinely caught. What it invalidates is the *evidence*:
every "caught" the original drills reported was unverified, and the same mechanism will report
"survived" for a guard that does fire. **Every mutation drill run in this repository before
2026-10-30 has this exposure.**

**Why this is the most important finding in the window.** Sabotage-the-guard is a standing working
method here and it has caught real would-have-shipped defects. This is a defect in the *instrument*,
not in any code it was pointed at — and an instrument that reports the right answer for the wrong
reason is indistinguishable from one that works until the day it is not. Recorded on #518 pending a
tier and a remedy; the remedy is a line in the practice (clear `__pycache__`, or advance the mtime
with `touch`), not code.

## What we found: the good

### 1. A pre-registered criterion decided a question the author had a stake in

#501's strided-memmap hypothesis is the author's own, and the refutation threshold was committed to
the issue before any production figure existed. `scan` came in at 47.5% against a 25% refutation
line, so the explanation survived — and it survived a test that could have killed it, which is the
only kind of survival worth reporting.

### 2. A premise was checked before a hypothesis was tested

The spike's hypothesis depended on an 8 GB RAM boundary that does not exist on the box. Measuring
the hardware before running the experiment is the single reason this window did not produce a
confident wrong answer about buying memory.

### 3. Verification by artifact, not by checkmark

`publishing_to_pypi.md` §C step 4 requires confirming a publish by installing the published artifact
into a clean venv. **It paid for itself immediately.** The first clean-venv install **failed** —
PyPI's JSON API still reported 1.15.0 as latest and `==1.16.0` was unresolvable about a minute after
a green publish. The upload log showed both files uploaded successfully, so it was index caching, and
a retry with `--no-cache --refresh` succeeded. But a genuinely failed publish would have presented
**exactly the same green tick**. The verification then went past the version string to behaviour:
the clamp produces 35.0, 65.0, 120.0, 120.0… with jitter pinned to its maximum, which is review fix
3 working in the shipped artifact.

### 4. A fix was declined with a reason rather than taken because it was available

A cause now exists for `scan`, and the spike's terms forbade optimising. Nothing was changed in
chunking, compression, the slicing pattern or the integrity check — the last of which is an
ADR-011/C-144 guarantee that must not be weakened to buy time.

### 5. A cross-repository seam closed on identity rather than cardinality

A peer session asked for the `land_gaul` member set to close a coverage check. Emitted through the
package's public API: **64,742** cells, with `land` at 64,818, `land_gaul ⊆ land`, and the difference
exactly **76** — matching the complement another repository holds as a tripwire. The peer's set
difference against the two delivered FAO parquets came back **zero both ways at both grains**. The
chain definition → tripwire → delivered bytes has never before been closed on identity.

### 6. An obligation's failure was found by a check not looking for it

ADR-043:99 requires any delivery containing supplemented cells to disclose their synthetic negative
GAUL codes and Natural Earth provenance. Six cells are affected (182470, 183190, 183909, 183910,
186058, 186778 — four Azorean islands). The obligation existed only as ADR prose: no mechanism, no
note in `consumer_data_guide.md`, no check. A downstream consumer had documented those codes with the
wrong cause for months, and measured that **nothing else in either delivered file is negative** —
which is what turned a documentation chore into a factual correction. This is the same spine as
C-72, in a different domain.

## What we found: the gaps

### 1. `write` is 48.2% of the export and wholly unexplained

Larger than `scan`, and untouched by any remedy identified for `scan`. Candidates named and untested:
compression settings, and the 12×360×720 chunking against a 3.1 GB store
(`docs/ADRs/041_content_addressed_skip.md:122`). The release records a cause for the smaller half of
the export and no cause for the larger half.

### 2. Two release-checklist steps were skipped and passed by luck

`publishing_to_pypi.md` §C steps **0** (credential review against ADR-026 §7) and **0b** (dispatch
any workflow lacking a `pull_request` trigger before promoting) come *before* the version bump. Both
were skipped and both passed when finally run. **Passing by luck is not passing by process**, and
nothing in the pipeline notices a checklist step that was never executed.

### 3. One link in the deploy verification is unproven

The deployed source on the box contains the 429 carve-out, and `git describe --exact-match` reports
`v1.16.0` on a tree whose artifact was behaviourally verified from PyPI. What was **not** executed is
a probe importing the deployed module in the server's own venv — the auto-mode classifier blocked it
as a production read, and it was not routed around. The editable-install `.pth` and the
`views_datafactory-1.16.0.dist-info` make the conclusion near-certain. Near-certain is not measured,
and after this window that distinction has earned its wording.

### 4. The hardware premise is wrong in 13 places and only one was corrected

The spike corrected its own premise and recorded the measurement. The 13 occurrences across 11
files, and ADR-030 and ADR-035 resting on "8 GB", are unchanged. The next person to reason from any
of them will reason from a false premise, exactly as the spike nearly did.

### 5. The machine ran out of memory during the release

Available memory on the development box reached **453 MiB of 31 GiB**, and Claude Code reaped a
background CI watcher as a result. It was reported as a memory reap rather than a build failure,
which is correct, but it is adjacent to C-345: an OOM-killed pytest exits **137** and prints no
`FAILED` lines at all. A release conducted under memory pressure is a release where the most
dangerous failure mode is silent.

### 6. `Closes #N` closed a story that is not finished

The promotion to `main` auto-closed **#517**, whose remaining steps at that moment were the tag, the
publish, the publish verification, the back-merge, the deploy and the harvest observation — that is,
all of them. It was reopened with its checklist restated. A closed release issue is a false
completion signal of exactly the kind this repository keeps finding in its own records.

## Release topology

`development` → `main` was merged as a **merge commit** (#521, `2ad3c22`), not a squash. A squash
would have rewritten the release SHAs, so `development` would no longer contain the released commit
as an ancestor and the `v1.16.0` tag would point into history `development` cannot reach (C-340).
Auto-merge was deliberately **not** armed: `gh pr merge --auto` silently refuses to change the method
on an already-armed PR, printing nothing and exiting 0, and the safe way to avoid that is not to arm
it.

`Release hygiene` detected the expected one-commit divergence and auto-opened **#524** — the third
instance after #505 and #495. The back-merge (#525, `main` → `development`, merge commit `c49cbfa`)
healed it, verified with `git merge-base --is-ancestor origin/main origin/development`; #524 closed
on a `workflow_dispatch` rather than waiting for the 06:00 cron, as #505 did. Two topology tests are genuinely red between promotion and back-merge and both carry their
own remedy in the assertion message, which is why the red is expected rather than investigated.
That is the mechanism working, and it is the C-320-compliant shape: transient, self-describing,
self-closing — not a permanent red that is indistinguishable from a broken build.

`publish_package.yml` is `on: release: published`, **not** on tag push, so pushing the tag published
nothing and the Release was the irreversible act. Its two version guards both ran: tag-equals-
pyproject, and newer-than-PyPI.

## What to do differently

1. **Clear `__pycache__` around every mutation step, or advance the mtime.** The drill is a standing
   practice and its results were unverified for an unknown number of prior windows. This is the
   cheapest high-value change in the list.
2. **Do not let the author audit their own guards.** The four defects were found by an independent
   review and the drill flaw by chasing a failure the author wanted to dismiss as an isolation
   quirk. The `falsify` guard mode exists for this and is normative about running in a clean context
   for exactly this reason.
3. **Run checklist steps 0 and 0b before the bump, not after the audit notices.** They are cheap,
   they are already written down, and they were skipped in a window that otherwise followed the
   procedure closely.
4. **Explain `write`, or stop quoting the export as understood.** A cause for 47.5% and no cause for
   48.2% is not an explanation of the export.
5. **Correct the hardware premise in all 13 places, or amend ADR-030 and ADR-035 to stop resting on
   it.** One corrected premise in a spike report does not stop the next reader reasoning from the
   twelve that remain.
6. **Give ADR-043's disclosure obligation a mechanism.** A better sentence in the ADR would
   reproduce the failure exactly. The shape that works is a check that fails when a delivered
   artifact carries supplement codes the consumer-facing documentation does not name — the
   consumer repository is adding precisely that on its side, and `consumer_data_guide.md` is the
   document on ours that should have carried it and did not.
7. **Do not conduct a release at 453 MiB free.** The failure mode under memory pressure is a silent
   137, and the whole release rests on reading test results correctly.
