## The thing to read if you read nothing else

**Every package in the chain did the right thing and the chain still delivered the wrong answer.**

views-frames 3.0.0 fixed reconciliation silently dropping a country's fatalities when its grid is
all zeros in a draw — **2.9–7.3% of fatality mass** on the first production run
(views-frames#283). views-pipeline-core 3.4.0 widened its pin and raised its floor to carry the
fix. views-baseline 1.0.3 widened its pin. Both published. And a fresh resolve of the
views-models forecast lane still produced **views-pipeline-core 3.3.5 and views-frames 1.11.0** —
the unfixed reconciler — with **exit 0 and no warning**, because views-datafactory declared
`views-frames>=1.10.2,<2` and every sparrow and condor member of views-models requires
`views-datafactory>=1.13.0`.

Nothing was broken. No test failed anywhere. The resolver did exactly what a resolver does: it
found the newest set of versions satisfying every constraint, and the constraint that bound was a
cap in a library that does not reconcile and had no stake in the question.

The second half is worse. This repository had a guard built specifically to catch a frozen
views-frames — `tests/test_dependency_floors.py`, added as C-337's fix — and it was green
throughout. It was green because it was correct about the thing it checked and the thing it
checked was the wrong one. Registered as **C-365**.

**This release was not found by this repository.** It arrived as a cross-session request from two
peers, one of which had measured the lane's resolution twice. No audit here would have found it.

## What we did

Investigated #527 read-only first, answered the four questions the `frames` session asked plus one
it did not, took the decision to the operator with the measurements attached, then released.

The investigation was deliberately read-only until the operator chose a shape. Two peer sessions
had asked for **different** changes — `frames` for cap-only (`<4`, floor kept), `baseline` for a
floor raise (`>=3.0.0,<4`) — and `baseline` additionally asked for the merge and the release. A
peer cannot authorise a release. Both options were put to the operator with measured consequences;
`baseline` then withdrew its request on its own, having read the same evidence.

## What shipped

One declared dependency range. No library code.

`views-frames>=1.10.2,<2` → `>=1.10.2,<4`, the lock moved to views-frames 3.0.0, one stale test
exemption deleted, one ADR amended, one plan addendum, version 1.16.0 → 1.17.0.

### The floor deliberately did not move

The `>=3.0.0` floor belongs where reconciliation happens — views-pipeline-core 3.4.0 carries it.
This package does not reconcile, and it is widely installed — 28 views-models requirements files
depend on it — so a `>=3.0.0` floor here would make it stricter than any sibling and force 3.x on
consumers with no reason to move. views-baseline 1.0.3 shipped exactly this shape.

**Correction, from `models`' independent confirmation (2026-11-02).** This post-mortem first said
that pipeline-core's floor "is what actually forces the fix into the lane" and that our widened cap
"only stops blocking it". That undersells the cap. `models` re-resolved the lane's **existing**
floors against the published 1.17.0 and got views-frames 3.0.0, pipeline-core 3.4.0,
views-datafactory 1.17.0, views-baseline 1.0.3, exit 0 — **with no views-models change at all**.
Removing the cap is sufficient on a fresh resolve, because a newest-preferring resolver then picks
pipeline-core 3.4.0, whose own floor pulls frames 3.0.0 in. Pipeline-core's floor *guarantees* the
fix rather than *enables* it, and the distinction matters: the floor raises in views-models earn
their place on a **reused** venv, which is never re-resolved — and that is the case this lane
actually hits. Both statements are true of different environments, and the original wording
collapsed them.

This matters for a reason beyond politeness: **a floor and a cap fail differently.** A too-low
floor admits old semantics silently (C-337). A too-low cap blocks new semantics silently (this
release). Only the second is a correctness problem for *other people*, which is why the cap moved
and the floor did not.

### Crossing views-frames 2.0.0 and 3.0.0 cost no code, and that is a measurement

views-frames 2.0.0 (its ADR-028) requires a frame's `index` to be a real `SpatioTemporalIndex`,
makes `frame.values` read-only, and makes `map_estimate` reject non-finite draws. None of the three
reaches us, and each was checked rather than assumed:

| ADR-028 change | How it was checked | Result |
|---|---|---|
| `index` must be a real `SpatioTemporalIndex` | read both construction sites | both already pass one |
| `frame.values` read-only | grepped every `.values` occurrence in `src/`, `scripts/`, `tests/`, `examples/` | every one is a read; confirmed on 3.0.0 that the array is non-writeable and an in-place write raises `ValueError` |
| `map_estimate` rejects non-finite draws | `tests/test_views_frames_floor.py` asserts the import surface is exactly six symbols | no estimator imported anywhere |

Against views-frames 3.0.0 in a clean venv: **2,437 passed, 16 skipped, 13 xfailed, 0 failed**,
`PYTEST_EXIT=0`; `mypy --strict` clean across 89 source files; `ruff` clean; `uv lock --check`
clean; `docs/validate_docs.sh` PASSED.

**ADR-050's fixture drift alarm did not fire**, which is information rather than silence. That test
regenerates the committed FeatureFrame fixture and compares bytes, and it exists to go red when a
views-frames upgrade changes the on-disk layout. Passing under 3.0.0 means 3.0.0 writes a
byte-identical layout across a two-major jump. A guard that *can* fail, not firing, is evidence; a
guard that cannot fail, not firing, is nothing — which is the distinction C-365 is about.

### A wider cap does not move the lock

Worth its own heading because it is the difference between a fix and a claim, and the naive version
of this release would have got it wrong.

`uv lock` keeps an existing pin while it still satisfies the constraint. Both candidate pins were
tried in scratch trees built from `git archive HEAD`:

| pin | after `uv lock` | consequence |
|---|---|---|
| `>=1.10.2,<4` | lock stays **1.10.2** | the wheel declares 3.x compatibility that CI never tested — **C-337 exactly** |
| `>=1.10.2,<4` + `--upgrade-package views-frames` | lock **3.0.0** | one guard red: `test_allow_list_has_not_rotted` |
| `>=3.0.0,<4` | lock **3.0.0** | `AUDITED_FLOOR` must change; over-constrains consumers |

The middle row shipped. Had the first row shipped, every gate would have been green and the release
would have been a lie — the same shape as v1.16.0's post-mortem thesis, arriving by a completely
different route one release later.

## Incident: the guard built to catch this was green for ten weeks

Registered as **C-365**; narrative in `register_changelog.md`. The short form:

C-337's fix added `tests/test_dependency_floors.py`, which flags any runtime dependency whose lock
resolution equals its declared floor. On 2026-08-21 views-frames legitimately sat on its floor —
1.10.2 *was* the latest release — so the same PR added an `ALLOWED_AT_FLOOR` exemption with a
written reason, and `test_allow_list_has_not_rotted` to expire it.

The reason had two clauses: *"the floor IS the latest release"* and *"remove this entry once
views-frames publishes past 1.10.2 and the lock moves."* **Those clauses can come apart, and they
did.** Upstream published 1.11.0, 2.0.0, 3.0.0 — the first clause became false. The lock never
moved, because the exemption was the thing that stopped anything asking it to — so the second
clause never fired.

The rot check expires an exemption against the **wrong referent**: it watches the thing the
exemption protects (the lock), not the thing the exemption's reason depends on (upstream). Ten
weeks, no error, and the consequence was 2.9–7.3% of the forecast's fatality mass arriving wrong.

**No mechanism is proposed, deliberately, and that is stated rather than hidden.** Detecting
"upstream moved past our cap" means querying an index at test time: a network call in the suite,
and a guard whose colour depends on something outside the repository, with no admin override on a
protected branch. That is C-320's permanently-red CI. The alternatives are out-of-band (a
dependency bot, which cannot redden CI) or documentary (requiring each exemption's reason to name
what will observe it ceasing to be true — which a test can check the presence but not the truth
of). The replacement comment in `tests/test_dependency_floors.py` states that obligation.
Registering a guard that cannot fire would reproduce the defect being registered.

**The transferable shape:** an exemption is a claim about the world with an expiry nobody set.
Every allow-list, skip-list and known-failures file in this repository has this available to it.

A dated addendum went on C-337 rather than reopening it. Its stated defect really is fixed. But a
resolution that cites a guard is only as good as that guard's referent, and nothing was checking
the referent.

## Incident: two guards caught the author during the release

Both are recorded because the release's value as evidence depends on them being visible.

### 1. The suite was run before the version bump and reported as the release's evidence

`TestF7ProductPlanCurrency` compares `reports/product_development_plan12.md`'s title against
`[project].version`. The local full suite had been run while the version was still 1.16.0, so the
guard had nothing to flag. That run was then reported to the operator as the evidence for the
release. It was evidence for the pin change only.

CI went red on the promotion branch. The title said *"current through v1.16"*.

**The failure is not the stale title — it is reporting a pre-bump suite as a post-bump result.** A
version bump changes what some tests assert. Fixed with a real v1.17 addendum in the document's own
convention and the suite re-run after the bump.

### 2. The ADR amendment cited code by line number

`tests/test_docs_citations.py` rejected `grid_to_feature_frame.py:59` in the first draft of the
ADR-009 amendment. Line numbers rot on the next edit; three of the ten citations that guard
replaced already pointed at blank lines. Rewritten to name the two functions, both verified to
exist.

Neither reached `main`. Both were caught by guards written in this repository for exactly these
failures — which is the counterweight to C-365 and belongs in the same document.

### 3. Three watchers read a result wrong before one read it right

Not a guard catching anything — the opposite. Three successive CI watchers reported settled or
green when they were not: two tested `conclusion` for a literal `"PENDING"` when a running check
reports an *empty* conclusion, and one shell condition inverted. A fourth, comparing a count of
`status == "COMPLETED"` checks against the total, was correct. Separately, a suite run was piped
through `tail`, so `$?` was `tail`'s exit status and not pytest's, and only 25 lines were kept —
the run was re-done capturing the real exit code.

Nothing merged on a bad reading, because `mergeStateStatus` was `BLOCKED` throughout and GitHub
would have refused. But the protection came from the platform, not from the watcher, and this is
the C-345 class: *a piped exit status reported a failing suite as passing.* It recurred, in the
same session, after being registered.

## ADR-009 had been wrong for three months

Context item 7 named the range as `views-frames >=1.0,<2`. The floor moved to 1.10.2 on 2026-08-02
and nobody updated the ADR, so code and ADR disagreed for three months — which ADR-000 forbids.
The cap change made it wrong twice.

Amended by date with the original prose intact, plus a header pointer following ADR-030's
precedent, because the stale fact sits in Context and a reader who stops there would leave with a
constraint that is not declared anywhere.

Worth noting as a pattern rather than an incident: this is C-336's class, found by changing the
thing the ADR described rather than by any check. Nothing reads prose.

## Why this release was not deployed

The production host runs v1.16.0, which carries the 429 retry and the failed-harvest ledger entry.
v1.17.0 changes only a declared dependency range, and the server's installed environment does not
resolve against it — it installs from a lock at a tag. So the 21 November cron behaves identically
either way.

This is stated because the standing rule after C-343 is that writing a tag is not deploying, and
the correct answer to "did you deploy?" here is **no, and deliberately**. A release that does not
need a deploy is a different thing from a release whose deploy was forgotten, and the difference
has to be written down or the next reader cannot tell them apart.

## What to do differently

1. **Re-run the suite after a version bump, not before.** A bump changes what some tests assert.
   The rule is not "run the suite" but "run the suite on the tree you are shipping".
2. **Never derive a pass/fail from a piped exit status.** `cmd | tail` gives you `tail`'s status.
   This is C-345, registered, and it recurred in this session.
3. **When polling a status field, test the field that says "finished", not the one that says
   "how it finished".** An in-flight GitHub check has an empty `conclusion`, not a `PENDING` one.
4. **Widening a cap requires `--upgrade-package`.** `uv lock` alone keeps the pin. Add it to the
   publishing runbook as a step, not a footnote.
5. **An exemption's reason must name what will observe it ceasing to be true.** Not enforceable by
   a test; enforceable by review, which is why it is written into the file.
6. **When two peer sessions ask for different changes, put both to the operator with measurements
   rather than arbitrating.** `baseline` withdrew its own request after reading the measurements —
   which is a better outcome than being talked out of it.
7. **A release that needs no deploy must say so.** Otherwise it is indistinguishable from a release
   whose deploy was forgotten, which is C-343's whole subject.
