## What this post-mortem covers

The [first post-mortem](../pre_deploy_post_mortem.md) covered GHS-POP implementation (v1.2.15). This one covers everything between "code works locally" and "pipeline runs on the server" — three version bumps, five PRs, two new ADRs, and the deployment itself.

Two foci:

1. **Deployment lessons** — what we learned and had to change once we actually deployed to Hetzner.
2. **Pre-deployment accuracy** — what our pre-deployment process (falsification, code review, risk register) got right and wrong, and what that teaches us about the process itself.

## Part 1: What we learned and changed during deployment

### The OOM saga: three fixes for one problem

The v1.2.15 post-mortem reported C-165 as "RESOLVED" — we had cast float64 to float32 at read time, dropping peak RSS from 22 GB to 7.4 GB. This was wrong. It took three more releases to actually solve the problem.

**v1.2.16: Strip-based raster aggregation (PR #55)**

The float32 cast reduced array size but didn't address the aggregation path. `_aggregate_to_prio_grid` called `data.copy()` on the full globe array — 6.88 GB + 6.88 GB = 13.76 GB peak for float64. Even with float32, `data.copy()` doubled the 3.44 GB array to 6.88 GB, leaving ~1 GB headroom.

The fix was `_aggregate_with_alignment`: process one PRIO-GRID row (60 pixel rows) at a time. Peak memory drops to raw array + ~20 MB working buffer. This eliminated the copy entirely.

**Why the plan missed it:** The v1.2.15 plan estimated peak RSS as `raw + aligned = 14.8 GB` and fixed it to `7.4 GB` with float32. But the estimate didn't include the `.copy()` inside `_aggregate_to_prio_grid`. The function was inherited from an early prototype and nobody traced its memory behavior — we only checked the caller's allocations.

**v1.2.17: Deferred float32 conversion (PR #56, then PR #57)**

With strip-based aggregation, the float32 cast at read time became counterproductive. `page.asarray()` returns float64. Casting the full 6.88 GB array to float32 requires holding both in memory simultaneously: 6.88 GB (float64) + 3.44 GB (float32) = 10.32 GB peak — OOM on 8 GB.

The fix was to remove the float32 cast entirely. Strip-based aggregation processes float64 data directly, converting to float32 only at the strip output level (60 pixel rows at a time). Peak is now: 6.88 GB (raw float64) + ~20 MB (strip buffers) = ~6.9 GB.

**Why the plan missed it:** The v1.2.15 fix (`astype(np.float32, copy=False)`) relied on `copy=False` performing an in-place conversion, but `copy=False` only avoids a copy when the array is already float32. For float64 → float32, it always allocates. The fix was "correct" only in a vacuum — it didn't account for interaction with the array that `page.asarray()` returns.

**v1.2.18: Thread control + accumulator cleanup (PR #57, PR #59)**

Two more memory savings, discovered by an 8-expert code review + falsification audit:

1. `page.asarray(maxworkers=1)` — tifffile's default spawns a ThreadPoolExecutor that double-buffers ~400 MB of compressed strip data alongside the 6.88 GB output array. Limiting to 1 thread eliminates the buffering.

2. `del pgid_rows, month_id_rows, pop_count_rows` — the viewpoint builder accumulated ~34.8M rows in three Python lists (~6.5 GB) to build a Parquet table. After `pa.table({...})`, the lists were never referenced but stayed in memory until function exit.

**What this pattern teaches:** The OOM was not one bug. It was four independent allocation sites, any one of which could push the server past 8 GB. Fixing them sequentially (cast → strip → remove cast → thread control + del) meant each fix exposed the next bottleneck. A single `measure peak RSS` probe in the original plan would have caught all four, but we treated memory as a point estimate rather than a profile.

### ACLED 401 token refresh

The ACLED API started returning HTTP 401 mid-pagination during the deployment pipeline run. The harvester had no retry logic for auth failures — it treated 401 as a permanent error and aborted.

**Fix:** `_authenticated_request()` function that catches 401, refreshes the bearer token, and retries once. Added in the same PR (#59) as the harvest caching fixes.

**Why this wasn't caught pre-deployment:** We had never run a full ACLED harvest on the server before. Local testing used cached data. The 401 only manifests when a long-running pagination session (ACLED has millions of events) outlives the token TTL. No unit test can simulate this without mocking the entire HTTP session lifecycle — and the mock would test the mock, not the API.

**Lesson:** Some bugs are only findable in production. The correct response is fast recovery (the `_authenticated_request` pattern), not more pre-deployment testing.

### Harvest caching: C-182, C-187, C-188

Three bugs in the harvest cache layer, all discovered through falsification audits:

**C-182: Failed entries treated as cached.** `last_digest_for_version` returned the `content_digest` from failed ledger entries, causing subsequent runs to skip re-fetching failed sources. Fixed by introducing `_VALID_CACHE_OUTCOMES = frozenset({"success", "unchanged"})` and filtering on it.

**C-187: Digest-field shadow bug.** `last_digest` and `last_digest_for_version` assumed `entry.get(digest_field)` always returns a string for successful entries. But malformed entries (success with no digest) would return `None`, shadowing valid earlier entries in the reverse scan. Fixed by checking `digest is not None` before returning.

**C-188: GAUL admin has no failure ledger entries.** The shapefile harvester's `_write_variable` caught exceptions and logged them, but never wrote a ledger entry. A failed GAUL harvest was invisible to the provenance system. Fixed by adding `append_ledger_entry` with `outcome: "failed"` in the except block.

**What these three share:** All three are consequences of the caching logic evolving source-by-source without a shared contract. UCDP invented outcome vocabulary. ACLED adopted it partially. GHS-POP adopted it partially. GAUL didn't adopt it at all. ADR-032 (Harvest Idempotence and Caching) was written after these fixes to codify the contract: two-key cache, outcome vocabulary, `--force` semantics.

### CI failures: not "pre-existing"

Two tests failed in CI after the v1.2.18 merge to development:

1. `test_remote_zarr_has_last_valid_month_id` — HTTP 401 because CI has no `.netrc`
2. `test_at_least_one_model_found` — `FileNotFoundError` because CI has no `../views-models/` checkout

Initial response: "These are pre-existing CI failures." This was wrong and was corrected directly. We are the sole developers on this project. Everything in CI comes from this machine. If CI fails, we introduced the failure and didn't catch it. "Pre-existing" is not a valid category — it just means "we didn't catch it when we should have."

**Fixes:**
- Narrowed `except Exception` to `except (URLError, HTTPError, TimeoutError, OSError)` in the remote zarr test, added proper `pytest.skip` for network errors
- Added `if not MODELS_ROOT.exists(): pytest.skip(...)` before the assert in the model test

**Lesson:** Every CI failure is ours. No deferral, no "pre-existing" label, no merging around it. Fix it in the same PR.

### Mypy compliance: 6 errors across 4 packages

After merging to development, mypy (strict mode) found 6 errors:

| Error | Location | Root cause |
|-------|----------|------------|
| `no-any-return` | `digests_and_ledgers.py` | `entry.get(digest_field)` returns `Any` |
| `no-any-return` × 3 | `feature_frame.py` | `.shape[]` returns `Any` per numpy stubs |
| `no-any-return` | `temporal.py` | `.item()` returns `Any` per numpy stubs |
| `arg-type` | `defaults.py` + `dataset.py` | `parsed.hostname` is `str | None`, `netrc.authenticators()` wants `str` |

**Fixes:** Type annotations (`digest: str | None = ...`), `int()` wraps for `.shape[]`, `or ""` fallback for hostname.

**Why these weren't caught locally:** We ran `mypy` on individual changed files, not `uv run mypy src/` on the whole project. The `feature_frame.py` and `temporal.py` errors weren't in files we'd touched — they were exposed by upgrading numpy stubs in the same `uv lock` resolution.

**Lesson (restated from v1.2.15):** Run `uv run mypy src/` before claiming "ready." Still not doing it consistently. Adding to the mandatory pre-ship checklist.

### numpy 2.x compatibility

`np.trapz` was removed in numpy 2.x, replaced by `np.trapezoid`. The viewpoint builders used `np.trapz` for temporal interpolation. On the server (numpy 2.1), this raised `AttributeError`.

**Fix:** `getattr(np, "trapezoid", getattr(np, "trapz", None))` — try the new name first, fall back to the old name.

**Why this wasn't caught locally:** Local environment had numpy 1.x pinned. The server installed from the same `pyproject.toml` but resolved to numpy 2.x because it had no lockfile. The `uv.lock` file is committed but the server did `uv sync` which may resolve differently.

## Part 2: What we got right and wrong pre-deployment

### What the process got right

**1. Falsification audits caught the OOM before deployment.**

The first falsification round (v1.2.15) predicted F2 ("can the server hold this in memory?") as FAIL and was confirmed. Without this probe, we would have deployed v1.2.15 to Hetzner and discovered the OOM in production.

**2. The 8-expert code review found the remaining memory issues.**

After v1.2.17 (the float32 removal), an 8-expert code review identified three more memory risks: tifffile thread buffering, list accumulator retention, and `.to_pylist()` in compilation. All 8 experts converged: "these are corrections, not optimizations." This led directly to ADR-031 (Resource Ownership) and the remaining v1.2.18 fixes.

**3. The risk register tracked the OOM across versions.**

C-165 was opened during v1.2.15 falsification, updated in v1.2.16 and v1.2.17, and finally resolved in v1.2.18. The register provided continuity across 4 PRs and 3 version bumps — without it, the "is this actually fixed?" question would have been answered by gut feeling, not evidence.

**4. ADR-032 codified lessons before they were forgotten.**

The harvest caching bugs (C-182, C-187, C-188) were individually small fixes (one-liners). But the pattern — each source reimplements caching without a shared contract — was a systemic issue. Writing ADR-032 during the fix (not after) ensured the fourth source won't repeat the same bugs.

**5. The deployment guide worked.**

The Hetzner deployment guide had steps for tagging, pulling, running the pipeline, and verifying. Deployment was a matter of following documented steps, not improvising. The one gap (swap configuration) was caught by falsification and added before deployment.

### What the process got wrong

**1. The v1.2.15 OOM fix was declared "resolved" prematurely.**

The first post-mortem said C-165 was resolved. It was not. The float32 cast fixed one allocation path but left three others. We closed the risk register entry after testing locally — but local testing doesn't have the same memory constraints as the 8 GB server.

**Why this happened:** No memory profiling. We estimated peak RSS by arithmetic (`n_pixels × sizeof(dtype) × 2`) but didn't profile the actual pipeline with a tool. The estimate covered the two largest allocations but missed `data.copy()`, the thread pool buffers, and the list accumulators.

**What would have caught it:** Running the full pipeline under `memory_profiler` or simply watching `htop` during a local run with `ulimit -v` set to 8 GB. Not sophisticated — just something we didn't do.

**2. The float32 "fix" made things worse.**

v1.2.15 cast float64 to float32 at read time. v1.2.17 removed that cast because it actually increased peak memory (both arrays in memory during conversion). The "fix" was counterproductive — but it passed code review, passed tests, and the post-mortem praised it as the right solution.

**Why the review missed it:** `astype(np.float32, copy=False)` looks correct. `copy=False` suggests no extra allocation. But `copy=False` means "don't copy if the dtype already matches." For float64 → float32, it always copies. The reviewer (both human and AI) read the API semantics as "avoid copies" when the actual semantics are "avoid unnecessary copies."

**Lesson:** Read the numpy docs, not the parameter name. `copy=False` is one of numpy's most misleading parameters.

**3. CI failures were initially deferred as "pre-existing."**

Two tests failed after merge. The initial response was to label them pre-existing and move on. This was wrong on principle — we are the sole developers, so all failures are ours — and wrong on practice, because one of the tests had an overly broad `except Exception` clause that could mask programming errors.

**What would have caught it:** Running full CI locally before the merge. We ran `pytest` but not `uv run pytest` in a clean environment. The CI tests that failed require infrastructure (`.netrc`, sibling repos) that our development machine has but CI doesn't.

**4. mypy wasn't run project-wide before any merge.**

Six mypy errors appeared after merge. All were in files we didn't touch directly — they were exposed by transitive dependency changes. Running `uv run mypy src/` would have caught them all.

**This is the third time this lesson appears.** v1.2.15 had mypy errors in CI. This post-mortem documents the same problem. The lesson isn't "run mypy" — we know that. The lesson is: **knowing isn't doing.** We need to make it a gate, not a suggestion. The `/ship-it` skill checklist should include `uv run mypy src/` as a hard prerequisite.

**5. numpy 2.x compatibility was a surprise.**

`np.trapz` → `np.trapezoid` broke on the server. We didn't test against numpy 2.x locally. The lockfile should have prevented this, but the server resolved dependencies independently.

**What would have caught it:** `uv sync --frozen` on the server (uses the committed lockfile exactly) instead of `uv sync` (re-resolves). Or: testing locally with numpy 2.x.

**6. ADR-032 was written after the bugs, not before.**

The harvest caching bugs (C-182, C-187, C-188) all stem from the same root cause: no shared contract for cache behavior. If ADR-032 had been written when the second source (ACLED) was added, the third source (GHS-POP) would have been implemented against a defined interface, and the shapefile harvester (GAUL) would have been audited.

**Why it wasn't:** WET-before-DRY discipline says "write three times before abstracting." For code, this is sound. For contracts, it may be wrong — a contract's purpose is to prevent divergence, and by the third implementation the divergence has already happened. Consider writing the contract ADR at the second source, not the third.

## What we'd do differently next time

### For deployment

1. **Profile memory on a simulated 8 GB budget before tagging.** Use `ulimit -v 8388608` or `systemd-run --scope -p MemoryMax=8G` to run the pipeline locally with server-equivalent memory constraints. If it OOMs locally, it'll OOM on the server.

2. **Use `uv sync --frozen` on the server.** The lockfile exists for a reason. Don't re-resolve dependencies on deploy — use exactly what was tested.

3. **Run `uv run mypy src/` and `uv run pytest` in a clean environment before every merge.** Not "I should run this." Actually gate the ship-it process on it. Make the tool refuse to proceed without it.

4. **Don't close risk register entries until the fix is validated on the target environment.** C-165 was "resolved" three times. It was actually resolved when the pipeline ran on Hetzner without OOM.

### For pre-deployment process

5. **Write caching/contract ADRs at the second source, not the third.** WET-before-DRY is right for code abstractions. It's wrong for contracts — the whole point of a contract is to prevent divergence before it happens.

6. **Add a "memory profile" probe to every falsification audit.** Not "estimate peak RSS" but "what is the maximum RSS you can measure?" Estimation misses hidden allocations (`.copy()`, thread pools, Python object overhead). Measurement doesn't.

7. **Never use the phrase "pre-existing" for CI failures.** If CI fails, we introduced it. If it was failing before our change, we should have fixed it before our change. No exceptions, no deferral.

8. **Test against the server's numpy version.** Pin numpy in `pyproject.toml` to match what the server resolves, or test with both numpy 1.x and 2.x locally.
