## What this post-mortem covers

The pre-deployment post-mortem covered the sprint process: what we extracted, how we planned, what the overhead ratio was, and what the deployment risk profile looked like. This post-mortem covers what happened when v1.2.21 actually ran on the server.

The key question for a maintenance release is different from a feature release. For v1.2.20 (GHS-BUILT-S), the question was "does the new thing work?" For v1.2.21, the question is "did we break what already worked?" A refactoring release that changes internal structure but produces identical output is the best possible outcome. Anything else means the extraction introduced a regression.

**Short answer: the pipeline produced identical output. No regressions. No surprises in the production code.**

The deployment itself had three operational issues — all infrastructure, none code. This continues the pattern from v1.2.20: the code works; the deployment process has rough edges.

## What went right

### 1. Grid output identical — the refactoring introduced zero regressions

The grid shape is `(456, 360, 720, 53)`, the same as v1.2.20. The feature count is 53, the same as v1.2.20. The zarr store is 2.1 GB. The dataframe export produced 29,557,008 rows with the same 6 UCDP features. All 18 health checks passed.

This is the entire point of a maintenance release. The code changed internally — 5 new shared modules, 1 deleted module, 51 files touched — and the output didn't change. The pure copy-paste extraction strategy held: no subtle regressions, no drifted constants, no changed validation logic.

### 2. All extracted modules worked in production

Five new shared modules were used for the first time on the server:

None of these extractions introduced import errors, name resolution failures, or behavior changes. The `uv sync` on the server installed them correctly. The import chain from the extraction sources to the shared modules resolved without issues.

### 3. `datafactory_synthetic` deletion caused no issues

The deleted module was genuinely dead. No import failed, no test referenced it, no pipeline step needed it. The `pyproject.toml` change (removing it from the packages list) was picked up by `uv sync` without complaint.

### 4. `_load_source_grid` assembly refactor worked

The assembly script went from ~720 lines with 3 near-identical load-validate-align blocks to ~540 lines with a single `_load_source_grid` function called 3 times. The S-4 fix (moving imports to module level) prevented the `NameError` that the pre-planning falsification caught. Assembly produced the same 53-feature grid.

### 5. The deployment guide was followed correctly this time

After the v1.2.20 lesson (Claude reconstructed wrong deployment instructions from memory), the deployment guide was re-read in full before this deployment. The tag-based deployment gate, `uv sync`, and `refresh_pipeline.sh` were used exactly as documented. No improvisation.

### 6. tmux saved us from the SSH drop

The v1.2.20 lesson was applied: use tmux for pipeline runs. The initial tmux failure (see below) was resolved by the system reboot, and the pipeline ran inside tmux for the full 4 hours. No SSH disconnects interrupted the run.

## What went wrong

### 1. tmux failed on first attempt — `[exited]` immediately

After SSHing into the server, `tmux new -s deploy` started and immediately exited with `[exited]`. The tmux session could not be entered.

**Root cause:** The server had 31 pending updates including a kernel update, and was flagged with "System restart required." The combination of pending system updates and/or stale system libraries likely caused tmux's child shell to fail on startup.

**Resolution:** Applied all pending updates (`sudo apt update && sudo apt upgrade -y`) and rebooted the server (`sudo reboot`). After reconnecting, tmux worked normally.

**Impact:** ~10 minutes of delay. The tmux failure also caused confusion with the `tmux kill-session` command — the `-s` flag was incorrectly suggested (the correct flag is `-t`), adding to the friction.

**Lesson:** Before starting a deployment, check for pending system updates. If the server shows "System restart required," reboot first. A stale system state can cause surprising tool failures that are difficult to diagnose under deployment pressure.

### 2. SSH idle disconnect before tmux was established

The first SSH connection dropped with "client_loop: send disconnect: Broken pipe" before the deployment started — the same idle timeout issue documented in the v1.2.20 post-mortem. This time it was harmless because no pipeline was running, but it required a reconnect.

**Impact:** None — the user reconnected immediately.

**Lesson:** This is the third time SSH idle timeout has been observed across two deployments. Consider adding `ServerAliveInterval 60` to `~/.ssh/config` for the Hetzner host to prevent idle disconnects:

```
Host views-datafactory-00
    HostName 204.168.219.108
    User <your-user>
    ServerAliveInterval 60
    ServerAliveCountMax 3
```

### 3. Pipeline duration increased from 3.4h to 4.0h

v1.2.20 completed in 12,351 seconds (3.4 hours). v1.2.21 completed in 14,269 seconds (4.0 hours) — a 15.5% increase despite no new data sources and all harvests cached.

**Root cause (likely):** The refactoring changed module paths and function signatures, which invalidated internal caches. Stages that were partially cached in v1.2.20 (from the GHS-BUILT-S first run) had to re-run fully in v1.2.21 because the provenance digests changed — the code producing the output is at a different import path, so the content hash differs. Additionally, the system reboot immediately before the pipeline run means the OS page cache was cold (no filesystem data cached in RAM).

**Impact:** Low. The 18-minute increase is within normal variation for a 4-hour pipeline. The next run (when all caches are warm and the OS page cache is populated) should return to ~3.4 hours or faster.

**Lesson:** Expect a one-time cache invalidation after any refactoring release that changes module paths. This is correct behavior — the provenance system is doing its job by detecting that the producing code changed. Subsequent runs with the same code will be cached normally.

## Deployment process maturity

Three deployments in, the process is stabilizing:

### What is now reliable

1. **Tag-based deployment gate.** Used correctly in all three deployments (after the v1.2.20 near-miss where Claude initially suggested `git pull` instead).
2. **`refresh_pipeline.sh` orchestration.** Runs all 11 steps, handles errors, writes logs, runs health checks. No manual intervention needed during the pipeline.
3. **Health check coverage.** All 18 sources + export freshness SLO checked automatically. No manual verification required.
4. **Pre-deployment postmortems.** Written for v1.2.20 (GHS-BUILT-S) and v1.2.21 (maintenance). These force a risk assessment before deployment rather than after.
5. **Falsification-driven confidence.** v1.2.21 had 7 falsification audits before deployment (5 pre-planning, 2 post-execution). The deployment confirmed all probes' predictions.

### What still needs improvement

1. **SSH configuration.** Three SSH disconnects across two deployments. `ServerAliveInterval` should be configured.
2. **Server maintenance before deployment.** The tmux failure was caused by pending system updates. Check and apply updates before deploying, not during.
3. **tmux command syntax.** The `-s` vs `-t` flag confusion wasted time. Document the correct commands in the deployment guide.
4. **Cache invalidation expectations.** Refactoring releases that change module paths will invalidate provenance caches. The deployment guide should note that first runs after refactoring will be slower.

## What we'd do differently

### 1. Check for system updates before deploying

Add to the deployment guide's Quick Deploy section:

```bash
# 0. Check server health (before starting deployment)
ssh <your-user>@204.168.219.108
sudo apt update && sudo apt upgrade -y
# If "System restart required": sudo reboot, wait 30s, reconnect
```

This takes 2-3 minutes and prevents the tmux-style failures that waste 10+ minutes of confused debugging.

### 2. Configure SSH keepalives

Add `ServerAliveInterval 60` to the local SSH config for the Hetzner host. This prevents the idle disconnects that have occurred in every deployment.

### 3. Document expected cache invalidation for refactoring releases

Add a note to the deployment guide: "After a release that changes module paths (refactoring, extraction, package reorganization), the first pipeline run will be slower because provenance digests have changed. Subsequent runs will be cached normally."

### 4. Nothing else

The deployment worked. The grid is identical. All sources are healthy. The maintenance sprint's extractions are running in production without issues. The process improvements are all operational — SSH config, system updates, documentation.
