## What this post-mortem covers

The pre-deploy post-mortem for GHS-BUILT-S covered the implementation
process — what went wrong during development, the 6.6:1 overhead ratio,
and the checklist compliance gap. This post-mortem covers what happened
when v1.2.20 actually ran on the server: what worked, what broke, and
what the deployment teaches about our process.

One focus: **deployment was uneventful.** That is the story. The v1.2.18
deployment post-mortem documented 6 categories of deployment surprises
(OOM saga, ACLED 401, harvest caching bugs, CI failures, mypy errors,
numpy compatibility). This deployment had one operational issue (SSH
timeout) and zero code issues. Every lesson from v1.2.18 was applied.

## What went right

### 1. Zero deployment surprises in the production code

Contrast with v1.2.18: that deployment discovered 4 OOM allocation
sites, an ACLED 401 mid-pagination, 3 harvest caching bugs, 2 CI
failures, 6 mypy errors, and a numpy 2.x incompatibility.

This deployment discovered nothing. The code ran exactly as tested
locally. Every v1.2.18 lesson was applied:

- **OOM:** `_aggregate_with_alignment` (strip-based, proven on GHS-POP)
  reused without changes. `maxworkers=1` on tifffile reads. `del`
  accumulators after Arrow table creation. uint32 rasters are 3.4 GB
  uncompressed — well within 8 GB budget.
- **Harvest caching:** `_VALID_CACHE_OUTCOMES` filter, digest-field
  guard, and `outcome` vocabulary all inherited from GHS-POP's
  proven pattern.
- **numpy compat:** No `np.trapz` usage (GHS-BUILT-S uses linear
  interpolation via numpy primitives, not `np.trapezoid`).
- **mypy:** `uv run mypy src/` run before tagging. Zero errors.

### 2. The deployment guide worked again

Quick Deploy section followed exactly: tag locally, push, SSH in,
set deploy tag, fetch, checkout, sync, run. No improvisation needed.

### 3. Pipeline step numbering updated correctly

Step count went from 10 → 11 (step 7: GHS-BUILT-S). All step labels
renumbered. `refresh_pipeline.sh` and `test_operational_integration.py`
both passed — the C-192 enforcement test (operational integration must
not trail implementation) caught this during development, not during
deployment.

### 4. `compile_pregridded()` generality confirmed in production

The compilation function was reused with zero changes for the second
time. The WET-before-DRY decision from v1.2.15 is validated — we
wrote it twice (GHS-POP, GHS-BUILT-S) and confirmed the abstraction
holds before considering extraction.

### 5. Harvest was fast

64 seconds for 12 GeoTIFF epochs (~2 GB). JRC's servers are fast,
no auth needed, no rate limiting. Caching worked correctly on
subsequent checks (0 downloaded, 12 cached pattern visible in
other sources).

## What went wrong

### 1. SSH connection dropped during zarr export

The SSH session disconnected ("client_loop: send disconnect: Broken
pipe") during step 9 (zarr export). The assembly step (step 8) took
3,340 seconds (~56 minutes), and the zarr export is another long
operation — the combined time exceeded the SSH session's idle timeout.

**Impact:** None. The pipeline process continued running despite the
SSH disconnect (the process wasn't killed by SIGHUP — likely because
`sudo -u views-deploy bash -c '...'` creates a separate session).
The full pipeline completed successfully, as confirmed by
`tail -30 logs/refresh.log`.

**What would have prevented it:** Running inside `tmux` or `screen`
on the server. The pipeline takes 3+ hours; SSH connections should
not be assumed to survive that long.

**Lesson:** For pipeline runs >30 minutes, always use a terminal
multiplexer. Add this to the deployment guide's Quick Deploy section.

### 2. Initial deployment instructions were wrong

Claude initially provided deployment instructions that skipped the
tag-based deployment gate entirely — a plain `git pull origin main`
followed by `bash scripts/refresh_pipeline.sh`. This contradicts
the deployment guide's Quick Deploy procedure, ADR-022 (tagged
releases), and the `~/.views-deploy-tag` mechanism that
`refresh_pipeline.sh` enforces at startup.

**Impact:** None — the user caught the error before executing.

**Root cause:** Context loss from conversation compaction. The
deployment guide had been read earlier in the session but the
specific procedure was lost when the conversation was summarized.
Claude reconstructed the deployment steps from memory rather than
re-reading the documentation.

**Lesson:** Always re-read `docs/guides/hetzner_deployment_guide.md`
before giving deployment instructions, even if it was read earlier
in the session. The deployment gate exists precisely because "just
pull main" is the obvious-but-wrong default.

## What we'd do differently

1. **Use `tmux` or `screen` for pipeline runs.** Add to deployment
   guide's Quick Deploy section. SSH sessions cannot be assumed to
   survive 3+ hour operations.

2. **Re-read the deployment guide before every deployment.** Do not
   reconstruct procedures from memory. The guide exists because the
   procedure is specific (tag gate, `uv sync`, `--frozen` lockfile)
   and the obvious approach (`git pull && run`) is wrong.

3. **Nothing else.** The deployment worked. The pre-deployment
   process (falsification, code review, pre-deploy postmortem,
   integration guide) caught everything that needed catching. The
   production code was clean. The v1.2.18 lessons held.
