## Task 1: Configure Swap (C-173, Tier 3)

**Why:** The CPX32 has 8 GB physical RAM and no swap. Any transient memory spike above physical RAM causes an immediate OOM kill with no graceful degradation. Adding even 2 GB of swap provides a buffer for short spikes while the kernel's OOM killer can make a more informed decision (rather than killing the largest process immediately).

**Register ref:** C-173

### Steps

1. SSH to the server:
   ```
   ssh views-deploy@204.168.219.108
   ```

2. Create a 2 GB swapfile:
   ```
   sudo fallocate -l 2G /swapfile
   sudo chmod 600 /swapfile
   sudo mkswap /swapfile
   sudo swapon /swapfile
   ```

3. Make persistent across reboots:
   ```
   echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
   ```

4. Set swappiness low (prefer RAM, use swap only as safety net):
   ```
   sudo sysctl vm.swappiness=10
   echo 'vm.swappiness=10' | sudo tee -a /etc/sysctl.conf
   ```

5. Verify:
   ```
   free -h  # should show 2 GB swap
   swapon --show  # should list /swapfile
   ```

### Acceptance Criteria

- [ ] `swapon --show` lists a 2 GB swapfile.
- [ ] `/etc/fstab` contains the swapfile entry.
- [ ] `vm.swappiness` is 10.

## Task 2: SSH Access Policy (C-88, Tier 2)

**Why:** SSH is currently open to any IP address. The original risk register recommendation was to restrict to PRIO and Uppsala IP ranges via ufw or iptables.

**Register ref:** C-88

### Open Question

**The project owner is skeptical about restricting SSH to only PRIO/Uppsala VPNs.** Possible concerns include:
- Remote work from non-VPN locations would be locked out.
- VPN outages would prevent emergency access.
- IP ranges may change without notice from institutional IT.

### Options to Discuss

1. **IP whitelist (original recommendation):** Restrict SSH to known PRIO/Uppsala CIDR ranges. Most secure but least flexible. Requires a fallback mechanism (console access via Hetzner web panel).

2. **Key-only + fail2ban (moderate):** Disable password authentication entirely (if not already), enforce Ed25519/RSA keys, add fail2ban with aggressive thresholds (3 attempts → 24h ban). No IP restriction. Good security without VPN dependency.

3. **Port knocking or WireGuard overlay:** SSH listens on non-standard port or behind a WireGuard tunnel. Adds a layer without institutional VPN dependency.

4. **Hybrid:** Key-only + fail2ban now (quick), IP whitelist later when operational patterns are clearer.

### Deferred Steps

The specific implementation depends on the discussion above. When ready:

1. Audit current SSH config:
   ```
   sudo cat /etc/ssh/sshd_config | grep -E "PasswordAuth|PubkeyAuth|PermitRoot|Port"
   ```

2. Verify key-only auth is enforced:
   ```
   PasswordAuthentication no
   PubkeyAuthentication yes
   PermitRootLogin no
   ```

3. Install and configure fail2ban (if Option 2/4 chosen):
   ```
   sudo apt install fail2ban
   # configure /etc/fail2ban/jail.local with SSH jail
   ```

4. Configure ufw rules (if Option 1/4 chosen):
   ```
   sudo ufw allow from <PRIO_CIDR> to any port 22
   sudo ufw allow from <UPPSALA_CIDR> to any port 22
   sudo ufw deny 22
   ```

### Acceptance Criteria

- [ ] SSH access policy decision documented.
- [ ] At minimum: password authentication disabled, key-only enforced.
- [ ] fail2ban or IP whitelist (or both) active — per decision.
